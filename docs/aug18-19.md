## 2. Foxit eSign idempotency — **NO server-side idempotency**

Verdict: Foxit eSign has **no** idempotency key on the send-for-signature operation. Retrying a send can double-send. **Fallback confirmed as the plan anticipated: client-side dedupe ledger keyed on the plan token.**

Evidence (pulled from the OpenAPI spec behind `app.developer-api.foxit.com` and Foxit's published guides):
- The send operation is `POST /esign/api/v1/folders/createfolder` (host `na1.fusion.foxit.com`), body field `sendNow: true`. Its request schemas (`URLEnvelope`, `Base64Envelope`, `BaseEnvelopefromTemplate`) contain **no** `requestId`, `uniqueKey`, or `Idempotency-Key` field. The word "idempotency" appears exactly once in the entire 17,417-line spec — in a **billing-only** FAQ: *"Credit deduplication means that if the same request (identified by its request_id) is received more than once, **the API processes it** but does not deduct an additional credit."* I.e. the gateway dedups **credit charges**, not **side effects**.
- Foxit's own guidance is explicit that you implement it: *"You implement idempotency in your orchestration layer by generating a unique key per document job and checking it before re-processing. This is a design responsibility. The API doesn't handle it for you automatically."* (API-Driven Document Workflow Automation blog).
- Webhook delivery is also not deduped: *"a non-2xx response causes Foxit to retry delivery, which can create duplicate processing if your handler is not idempotent."*

Reconciliation hooks that make a client-side ledger work:
- `createfolder(sendNow:false)` creates a **DRAFT** folder and returns its `folderId` synchronously — the irreversible send is a separate step.
- `GET /esign/api/v1/folders/myfolder?folderId=` returns `folderStatus` ∈ {`DRAFT`, `SHARED` (=sent), `EXECUTED`, `CANCELLED`}. **`DRAFT` vs `SHARED` is the authoritative "did the send actually happen?" check** — exactly what a crash-safe `confirmExecuted()` needs.
- `GET /esign/api/v1/folders/getAllFolderIdsByStatus` lists folder IDs by status (reconcile by search when no folderId is known).
- Webhook events include `folder_sent`, `folder_signed`, `folder_cancelled`, `folder_completed` — handler must dedupe on `(folderId, event_name)`.

Architecture implication (two eSign API flavors exist — do not conflate them):
- **Gateway eSign** (`na1.fusion.foxit.com/esign/api/v1`, in the DevPortal reference): OAuth via `client_id`/`client_secret` headers; send is folded into `createfolder(sendNow:true)`. No documented programmatic send-draft endpoint on the gateway.
- **Legacy eSign** (`na1.foxitesign.foxit.com`, in `developersguide.foxitesign.foxit.com`): OAuth2 client-credentials token; **has** `POST /api/folders/sendDraftFolder` for the two-step create-draft-then-send.
- For the safe two-step flow we want (`createfolder(sendNow:false)` → persist `planToken → folderId` → send → confirm), if the gateway flavor turns out to lack send-draft, use the legacy host for the send step, or verify with Foxit. **Decision to lock during Aug 20-22 adapter work, not now — the ledger design is identical either way.**

## 3. Nutrient DWS idempotency — **PARTIAL**: server-side key only on async `/build`

Verdict: Nutrient supports an `Idempotency-Key` header **only** on `POST /build` **when sent with `Prefer: respond-async`**. Synchronous `/build`, all `/processor/*` endpoints, and the entire Data Extraction API (`/extraction/parse`, `/extraction/extract`) have **no** idempotency mechanism. A retry after a lost response can execute and bill duplicate work.

Evidence (from the official OpenAPI spec behind `api/reference/public`, `openapi.json`, v1.17.0):
- `/build` async: *"Optional idempotency key for async Build API admission. Reusing the same key with the same request payload and relevant headers returns the original async job. Reusing the same key with different work returns `409 Conflict`. The key must be non-empty, supplied at most once, and no longer than 255 bytes."* Error codes: `invalid_idempotency_key` (400), `idempotency_key_conflict` (409), `idempotency_admission_in_progress` (409). Async jobs give a `job_id`, `status_url` (`GET /async/jobs/{jobId}`), `result_url`, and `job_access_token`; keys are reusable after the job-metadata retention window. **Not supported on test keys.**
- **Every other DWS operation is a plain POST with no dedup parameter** (enumerated across the whole spec). Data Extraction has no OpenAPI spec at all — docs only — and no job ID or status-query endpoint; responses carry a server-generated `requestId` for support correlation only.
- `requestId` in error bodies is diagnostics, not an idempotency key (*"an internal ID we attach to each request"*).
- Billing: Processor FAQ says failed requests (4xx/5xx) are **not** charged and retries with exponential backoff are recommended; a failed retry is not double-billed, but two **successful** executions of one logical operation would be. Data Extraction bills per page (`usage.cost` reported per response) with no documented uncharged-failure guarantee. Response headers `x-pspdfkit-request-cost` / `x-pspdfkit-remaining-credits` let the ledger audit actual spend.

## The locked decision (this is what the core must implement)

**Baseline: client-side dedupe ledger, keyed on the core's plan token, for every irreversible-ish or billable vendor call. The vendor APIs do not give us idempotency where it matters.**

- **eSign send**: two-step — `createfolder(sendNow:false)` → persist `{planToken → folderId}` in the durable journal *before* sending → send (gateway `createfolder(sendNow:true)` or legacy `sendDraftFolder`) → on restart/retry, look up token; if `folderId` exists, `GET myfolder` and send **only if `folderStatus === DRAFT`**; if a row exists with `SHARED`/`EXECUTED`, never re-send and mark executed. `"executed"` audit only after `folderStatus` confirms `SHARED` (or after the `folder_sent` webhook, deduped on `(folderId, event_name)`).
- **Nutrient extraction/redaction**: per-operation dedup with an explicit ledger state machine — derive the operation key (SHA-256 of document bytes + instructions/schema) and persist the operation as `prepared`/`in_flight` *before* calling the vendor; transition to `done` only after the vendor returns confirmed success (and record `usage`/`requestId` from the response). On crash/restart, any row still `in_flight` is reconciled before anything is skipped: re-check whether the vendor call actually succeeded (for sync calls, the retry-safe path is to re-run once — billing is per-success on the Processor API, and for Data Extraction the only unknown-outcome guard is re-query/retry), and only then decide `done` or retry. Never mark `done` pre-call. Retry only on transient failures (5xx, 429, 408, network) with exponential backoff, never on 4xx; log server `requestId` beside our key. Where a `/build` request is big or long-running, prefer async `/build` with `Prefer: respond-async` + our own `Idempotency-Key` and keep the local ledger for the job→result mapping.
- **The plan token stays the documented idempotency key** for eSign sends (per build-plan Aug 20-22 MUST list). For Nutrient, the per-operation digest is derived from the same plan token + operation + inputs so one token governs all its side effects.
